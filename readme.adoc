Watch and steer your Claude Code agents as little robots working in a round cartoon town.

Every Claude Code or GitHub Copilot session becomes a square-headed robot, coloured by the agent it comes from. When the agent reads files, its robot reads a tablet at the library. When it edits code, the robot hammers at the construction site and a tower grows. When it runs a command, sparks fly at the forge. When it needs you, it stops, waves and an exclamation mark pops up above its head. Click it to see who it is, what it is doing and what it needs.
The town's bank pays robots in animated gold coins: Claude earns tokens, Copilot CLI earns AI credits (AIC). The bank sums daily payouts, robot labels show their session earnings, and two optional glass vaults show provider limits separately.

== At a glance

[cols="1,3"]
|===
| What | A local web app that turns Claude Code and GitHub Copilot activity into an animated 3D town.
| Who for | People who run several AI coding agents at once and want to see, at a glance, who is working and who is waiting for them.
| How it gets data | Claude Code *hooks* (`type: "http"`) post events to a local server; transcripts provide tokens and a *status line* reports model, cost and plan limits. GitHub Copilot hooks run a forwarding script; local Copilot CLI usage checkpoints provide AIC without billing configuration. The optional premium-request vault uses the GitHub billing API. See <<hooks>>, <<bank>> and <<copilot>>.
| Where it runs | Only on your computer: server on `http://localhost:{server-port}`, town in your browser.
| Languages | Interface in English and Polish (switch in the top-left corner).
| Status | Stage 1 (watch) with the bank, and an experimental part of stage 2 (approve from the town). See <<status>>.
|===

== How the town works

=== Stations

The town is a round island. A fountain sits on the plaza in the middle, a ring road goes around it, and buildings stand on the outer ring.

[cols="1,1,3"]
|===
| Station | Claude Code tools (Copilot tools are mapped to these, see <<copilot>>) | What the robot does

| Library (purple dome) | `Read`, `Grep`, `Glob`, `LS` | Reads a glowing tablet. When the next step is an edit, it carries a crate to the construction site.
| Construction site (crane) | `Edit`, `MultiEdit`, `Write`, `NotebookEdit` | Hammers. Every edit adds part of a floor to a round tower. A finished tower gets a roof, confetti and is then rebuilt.
| Forge | `Bash`, `PowerShell`, `BashOutput`, `KillShell` | Strikes the anvil, sparks fly.
| Radar tower | `WebSearch`, `WebFetch` | Looks up; the dish spins and sends out signal rings.
| Plaza (fountain) | everything else (`TodoWrite`, MCP tools, `Task`…) and "thinking" right after a prompt | Works on a tablet next to the fountain.
| Charging station | — | A robot whose turn has finished stands on a pad and charges (sleepy eyes, green antenna light).
| Factory | — | New sessions roll out of its door. Ended sessions walk back in.
| Bank (columns, coin on the roof, two glass vaults) | — | Not a work station. Pays robots in coins at the end of each turn and shows how much of each limit is left. See <<bank>>.
|===

=== Robot colours

The robot's body colour tells you which agent it is:

* *Warm colours* (orange, amber, coral, pink…): Claude Code. The first one is orange `#e8794a`.
* *Cool colours* (blue, violet, teal…): GitHub Copilot. The first one is blue `#4d8dff`.

Robots of the same agent get different shades of its family, so they stay easy to tell apart. The legend explains the two families. The agent's name is in the robot's panel (first item of the line under its name) and in the tooltip of its name tag. Copilot robots also have a purple antenna bulb and a small purple "Copilot" mark on their name tag. The name tag shows the model once it is known ("Atlas · Opus 5.5"). The demo shows two Copilot robots (Nova, Pixel) among four Claude robots.

[[bank]]
=== The bank, daily payouts and earnings

The bank pays the robots for their work. These figures are deliberately separate:

* *Earned*: each robot's cumulative session payouts, shown in a compact gold coin badge below its name and in its panel. The badge shows just the amount and unit; its tooltip explains that this is the session's earnings. *Claude* earns tokens (input, output, cache write and cache read), paid at the end of a turn from its transcript. The panel separately shows currently read token usage, Claude Code's estimated dollar cost and context fill. *Copilot CLI* earns AIC from locally saved cumulative usage checkpoints (see <<copilot-aic>>), displayed to two decimal places. Coins and feed entries use the matching unit; the number of animated coins is cosmetic.
* *Paid out today*: the bank label, HUD chip and bank card show *Claude tokens* and *Copilot AIC* separately for the server's local calendar day. They are not converted or added into a single mixed-unit total. This needs no billing token or allowance setting. It covers tracked sessions, not all account or organisation usage.
* *What is left* of each provider's limit, in two glass vaults on the sides of the bank. Seen from the town centre, the left vault is Claude (accent `#d97757`), the right one Copilot (accent `#8b5cf6`).
** Claude: the coins show what is left of the 5-hour window; a thin ring marks what is left of the weekly window. From the Claude Code status line (Pro and Max plans only, after the first answer).
** Copilot: `1 - used / allowance` of this month's premium requests, from the GitHub billing API (`pnpm copilot:setup`, see <<copilot>>).
** Unknown: an empty grey vault.

A label above the bank and the chip next to the counters open the *bank card*: today's payouts first, then optional account limits, reset times and the estimated cost of live Claude sessions. Clicking the building does the same. Grey vaults do not prevent daily payouts from working.
The floating bank label has a small *Today* heading and two aligned rows: `Claude <tokens>` and `Copilot <AIC>`. It no longer puts a combined amount above empty provider-limit rows. Optional quotas remain in the bank card and the glass vaults.

Accounting totals still update as soon as usage arrives, but *the coin reward waits for the end of work*: `earned` updates accumulate while a robot works or needs input. Once its session is idle and it has finished its queued work animation, one batch of gold coins flies from the bank to it as it heads back to the charger (or while already parked). After every coin arrives, the robot cheers, its earnings badge glows and a gold `+amount` popup appears above its name, without covering its earnings. Delayed usage received after the turn also triggers a reward; reconnect snapshots never replay historical payouts. Switching modes or removing the robot clears pending visual rewards without changing the durable ledger.

Daily history and each session's cumulative high-water mark are saved together to `~/.agent-village/payouts.json` (or `AGENT_VILLAGE_HOME`), atomically with mode 600 every 5 seconds and on graceful shutdown. Restarting the server or rereading a transcript does not pay the same cumulative amount twice. Startup fails on a corrupt ledger instead of discarding it; save errors are reported in the server terminal. No prompts, paths or transcript content are saved in this ledger. Demo payouts never touch it.

The day rolls over at local midnight (updated within 5 seconds); lifetime session earnings are not reset. Claude payouts are attributed to the time the village observes them, not reconstructed historical token-use dates. On a tracked Copilot CLI session's first read, available checkpoints are imported in order and their increases attributed to each checkpoint's local date. An interval spanning midnight belongs to the day of its closing checkpoint; this is not a per-call billing report. Untracked sessions are not scanned. Missing older Claude subagent transcripts can delay further payouts until the observed cumulative total exceeds the saved high-water mark.

Unavailable Copilot AIC is shown as "—" with a reason, not invented zero. If a later read fails, the last known total stays visible with a warning in the robot panel.

=== Signals

* Yellow bubble *!* and a waving robot: the agent needs a permission (for example to run a command).
* Blue bubble *?*: the agent asked you a question (`AskUserQuestion`) or needs input.
* The antenna light blinks in the same colour, so you can spot it even when zoomed out.
* The chips under the counters (top right) list every robot that is waiting. Click one to jump to it.

=== Controls

* Click a robot (or its name tag) to open its panel: task, current step, recent steps and, when it is waiting, the request.
* The panel's *Session time* section shows lifetime, work, waiting for you, and idle time; see <<session-time>>.
* Drag to move the camera, mouse wheel or pinch to zoom, kbd:[Q] / kbd:[E] or the buttons to rotate by 45°.
* "Follow" in the panel keeps the camera on the robot. kbd:[Esc] closes the panel.
* The page follows your system's light or dark theme. Dark theme turns the town into night with lit windows and lamps.

[[session-time]]
=== Session lifetime and time breakdown

Each robot's panel has four live counters, shown in hours, minutes and seconds:

* *Lifetime*: wall time since this session ID was first observed by the timing feature. It includes gaps between village runs and freezes when a `SessionEnd` arrives. Resuming the same session ID continues its lifetime and totals.
* *Work*: time in `thinking` or `working` (model thinking and tools combined).
* *Waiting for you*: time in `waiting` or `asking` (a permission prompt or a question).
* *Idle*: time after a turn finishes or before the first prompt, awaiting the next task.

These are *observed session-state durations, not CPU time*. The last state remains in effect until another hook changes it; missing hooks cannot be reconstructed. In particular, if an approval is answered in the agent's terminal but there is no separate resolution event, waiting ends at the next relevant hook, which can be the tool's completion. Concurrent tools and subagents are not added together as separate worker-hours.

The server saves only session IDs, timestamps and accumulated durations to `~/.agent-village/session-times.json` (or inside `AGENT_VILLAGE_HOME`). It checkpoints every 5 seconds and flushes on graceful shutdown, using atomic replacement and file mode 600. No prompts, project paths, tool inputs or tokens are in this file. A broken history file stops startup with an error rather than silently resetting it; write errors are reported in the server terminal.

After a restart, an old robot reappears when the next hook for its session ID arrives, with its counters preserved. Different session IDs have separate totals. Intervals while the server was stopped or the session was no longer observed are *not* assigned to work, waiting or idle; the panel lists that difference as *Unobserved*. A crash can lose the interval after the last successful checkpoint (normally up to 5 seconds). The browser freezes at the last server update when disconnected. Earlier sessions from before this feature have no recoverable time breakdown: collection begins with the first observed event after installing it.

Demo counters start with the simulation, follow its state changes, and are never saved to disk.

== Quick start for everyone (no programming needed)

This takes about 10 minutes the first time. You need a Windows, macOS or Linux computer with Claude Code already working.

. *Install Node.js.* Go to https://nodejs.org, download the version marked *LTS* and install it with the default options.
. *Install pnpm.* Open a terminal (Windows: press kbd:[Win], type `PowerShell`, press kbd:[Enter]) and type:
+
[source,shell]
----
npm install -g pnpm
----
. *Get the project.* Either download it from GitHub as a ZIP and unpack it, or clone it with Git. Remember the folder.
. *Open a terminal in that folder.* Windows: open the folder in Explorer, click the address bar, type `powershell` and press kbd:[Enter].
. *Set everything up with one command* (only the first time):
+
[source,shell]
----
pnpm first-run
----
+
This downloads the parts the town needs, builds it and connects Claude Code and GitHub Copilot to it (it adds hooks and a status line to your Claude Code settings, with a backup saved first, and one hooks file for Copilot in `~/.copilot/hooks/`). A status line you already had keeps showing.
+
NOTE: Type `first-run`, not `setup`: `pnpm setup` is a built-in pnpm command that does something else.
. *Start the town:*
+
[source,shell]
----
pnpm start
----
+
Your browser opens `http://localhost:{server-port}`. Leave the terminal window open; closing it stops the town.
. *Use Claude Code or GitHub Copilot as usual*, in any project (Copilot: the `copilot` command line tool, or agent mode in VS Code chat). Sessions that you start (or restart) from now on appear as robots.

[TIP]
====
No agents running yet? Click *Demo* in the top-right corner to see six simulated robots at work.
====

To stop the town, press kbd:[Ctrl+C] in its terminal. To disconnect Claude Code and Copilot from the town completely, run `pnpm hooks:uninstall` in the project folder (your previous status line comes back).

Optional: to fill the Copilot vault of the bank with this month's premium requests, follow <<copilot-vault>>.

=== Approving requests from the town (optional, experimental)

By default the town only watches: when a robot waves, you answer in the Claude Code terminal as usual.
If you want *Allow* / *Deny* buttons in the town that really answer Claude Code, run once:

[source,shell]
----
pnpm hooks:install --approvals
----

and restart the town with `pnpm start`. When Claude Code asks for a permission, it now waits up to 60 seconds for your click in the town. If you do not click, Claude Code shows its usual question in the terminal.

== Quick start for developers

.Requirements
* Node.js *{node-min} or newer* (the server runs TypeScript directly through Node's built-in type stripping).
* pnpm {pnpm-ver} (`npm install -g pnpm` or `corepack enable`).
* Claude Code with HTTP hook support, for live data. The demo works without it.

[source,shell]
----
pnpm install          # dependencies for the web town and type checking
pnpm dev              # server on :4747 (auto-restart) + Vite on :5173 with hot reload
pnpm hooks:install    # connect Claude Code to the local server (user settings)
----

Open `http://localhost:{dev-port}` during development. Vite proxies `/events` and `/api` to the server.

| `pnpm first-run` | `pnpm install`, `pnpm build`, `pnpm hooks:install` in one go. (Not named `setup`, because `pnpm setup` is built into pnpm.)

| `pnpm serve` | Starts the server without opening a browser.
| `pnpm dev` | Server with `--watch` plus the Vite dev server.

| `pnpm check` | `test` + `typecheck` + `build`. Run before every commit.
| `pnpm hooks:install [--approvals] [--port N] [--project DIR] [--claude\|--copilot] [--no-statusline]` | Adds the hooks and the status line to Claude Code settings and writes the Copilot hooks file (Copilot is skipped with `--project`). `--claude` / `--copilot` (same as `--only claude\|copilot`) do one side only.

The server can also run without `pnpm install`: `node packages/server/src/index.ts`.

== Instructions for AI agents

You are working on Agent Village. Read this whole file before changing anything. Then follow these rules.

. *This file is the source of truth.* If your change alters behaviour, commands, the event model, files or plans, update the matching section here in the same change, and update <<status>>. Do not create other documentation files; add sections here instead.
. *Keep the server and the shared package dependency-free.* They use only Node's standard library and run as `.ts` files through Node type stripping. That means: erasable TypeScript only (no `enum`, no `namespace`, no constructor parameter properties), `import type` for types, and explicit `.ts` extensions in relative imports. The shared TypeScript config enforces erasable syntax in the web package too, so keep the same style there.
. *Never weaken the security model* (<<security>>): loopback binding by default, Host header check, token on hooks and API, no CORS. Ask the human before changing any of it.
. *Hooks must stay fast and harmless.* Observation hooks must answer immediately with an empty body. Only `PermissionRequest` may wait, and only when approvals are on. Any error path must let Claude Code continue normally.
. *The UI is bilingual.* Every user-facing string goes into `packages/web/src/ui/i18n.ts` with both `pl` and `en`. Polish strings that depend on the robot's grammatical gender use `{ m, f }`.
. *The shared contract is `packages/shared/src/index.ts`.* Change server and web together when you change it, and bump `PROTOCOL_VERSION` for breaking changes.
. *Before you finish*, run `pnpm check` (or at least `pnpm test` and `pnpm typecheck`) and fix what fails. For visual changes, run `pnpm dev`, use *Demo* mode and look at the result.
. *Keep changes small and explain them* in the commit message: what changed and why.
. *The human author is the only author.* Do not add `Co-Authored-By:` trailers, "Generated with …" lines, session links or any other AI attribution to commits, pull requests or files. Commits go to the private repository https://github.com/dbartocha/Agents-Village. See <<author>>.

== Architecture

[source]
----
 Claude Code session(s)                     your computer only
 ┌──────────────────────┐   HTTP POST /hooks   ┌──────────────────────────────┐
 │ hooks (type: "http") │ ───────────────────► │ Agent Village server :4747   │
 │ SessionStart,        │ ◄─── empty body ──── │  VillageState (sessions,     │
 │ PreToolUse, Stop, …  │      or decision     │  activities)                 │
 └──────────────────────┘   (PermissionRequest)│  PermissionBroker (approvals)│
                                               └──────┬───────────────▲───────┘
                                     GET /events (SSE)│               │POST /api/permissions/:id
                                                      ▼               │
                                               ┌──────────────────────┴───────┐
                                               │ Browser: the town            │
                                               │  Live/Demo source → Village  │
                                               │  → Robots → three.js + HUD   │
                                               └──────────────────────────────┘
----

* *Claude Code* sends a JSON payload for each hook event to `POST /hooks`, and its status line script sends the status line JSON to `POST /api/statusline`. The installer writes both for you. *GitHub Copilot* runs `scripts/copilot-hook.ts`, which posts to `POST /hooks/copilot`.
* After some hooks the server reads the session's Claude *transcript* to count tokens. Copilot hooks and a 5-second poll trigger incremental local CLI AIC checkpoint reads without delaying the hook response. If you ran `pnpm copilot:setup`, a separate optional poll asks the GitHub billing API for monthly premium requests every 10 minutes.
* *The server* turns each payload into *activities* (see <<event-model>>), keeps a picture of every session and of the bank in memory, and pushes changes to browsers over *Server-Sent Events*.
* *The town* builds robots from the snapshot it gets on connect, then animates each new activity. In *demo mode* a local script produces the same activities, so live and demo share one code path.

[[event-model]]
== Event model

The contract is defined in `packages/shared/src/index.ts`. Protocol version *2* (`PROTOCOL_VERSION`): sessions carry `provider` instead of `agent`, the snapshot carries `bank`, and there are the messages `bank` and `session` and the activity `earned`.

=== Session

One agent session (`session_id`) = one robot. Copilot session ids get the prefix `copilot:`. The server keeps for each session: `id`, `provider` (`claude` or `copilot`, from the hook that created it), robot `name` (from a fixed list: Atlas, Nova, Bolt, Iris, Pixel, Luna, …), `cwd` and `project` (last folder name), `model` (id, e.g. `claude-opus-5-5`, from the transcript or status line), `modelName` (display name from the status line, e.g. "Opus 5.5"), `usage` (`TokenUsage`: `input`, `output`, `cacheWrite`, `cacheRead`; `totalTokens()` adds them up), `costUsd` (Claude Code's estimate), `contextPct` (0–100), `status`, last `prompt`, `currentTool`, `pending` permission, `attentionText`, number of running `subagents`, `toolCount`, `lastMessage`.

The *bank* (`Bank`) has `claude` (`fiveHour` and `sevenDay` windows with `usedPct` 0–100 and `resetsAt` in epoch milliseconds, an optional `spend` limit, `updatedAt`) and `copilot` (`used`, `allowance`, `month` like `2026-10`, `updatedAt`, and `error` when the last check failed; `updatedAt: 0` means it never worked yet).

Additive protocol-2 payout fields: `SessionInfo.earnings` is `{ unit: 'tokens' | 'nanoAic', total }`, optionally accompanied by `earningsError`. `Bank.daily` is `{ day: 'YYYY-MM-DD', tokens, nanoAic }`. Amounts are nonnegative safe integers; one AIC is `1_000_000_000` nano-AIC. An `earned` activity carries either `tokens` or `nanoAic`, never a mixed amount. Unknown session earnings remain absent.

`status` is one of: `idle` (turn finished, waiting for your next prompt), `thinking` (between steps), `working` (a tool is running), `waiting` (needs a permission), `asking` (asked you a question), `ended`.

The additive protocol-2 field `timing` contains `startedAt`, `since`, accumulated `workMs`, `waitMs`, `idleMs`, the optional running bucket `active`, and optional `endedAt`. Shared helpers settle the previous bucket before each status transition and let the UI interpolate between updates without mutating the totals. Old servers without `timing` show an explicit "no timing data" hint instead of invented counters.

=== Hook → activity mapping

[cols="2,2,3"]
|===
| Claude Code hook | Session status | Activity and robot behaviour

| `SessionStart` | idle | `session_start`: robot rolls out of the factory to a charging pad.
| `UserPromptSubmit` | thinking | `prompt`: robot cheers, leaves the charger, thinks at the plaza. The prompt becomes its task.
| `PreToolUse` | working | `tool` with `station` and a one-line `target`: robot walks to the station and works.
| `PreToolUse` for `AskUserQuestion` | asking | `tool` + `attention: question`: robot waves with a blue *?*.
| `PermissionRequest` | waiting | `permission`: robot waves with a yellow *!*. With approvals on, the HTTP call is held until you click (or until the timeout).
| `Notification` with `notification_type: permission_prompt` | waiting | `attention: permission` (watch-only variant of the above).
| `Notification` with `idle_prompt` | idle | `attention: idle` (logged only).
| `Notification` with `agent_needs_input` / `elicitation_*` | asking | `attention: question`.
| `PostToolUse` | thinking | `tool_done`. An open permission is closed as answered in the terminal.
| `PostToolUseFailure` | thinking | `tool_failed` with a short error.
| `Stop` / `StopFailure` | idle | `stop` with the last assistant message: robot goes to charge once its queued steps are shown.
| `SubagentStart` / `SubagentStop` | — | `subagent_start` / `subagent_stop`: counter on the robot.
| `SessionEnd` | ended | `session_end`: robot walks back into the factory and disappears after 15 s.
| ~1.5 s after `Stop` / `StopFailure` / `SessionEnd` | — | `earned` with `tokens` = tokens used since the previous `earned` (only when more than 0): coins fly from the bank to the robot. `PostToolUse` and `SubagentStop` also trigger a read, which only updates `usage`.
|===

Hooks fired inside a subagent carry `agent_id` and are attributed to the parent session's robot.

=== Messages on the stream

`GET /events` sends `event: snapshot` once (all sessions, the last 200 activities and the bank), then `event: activity` (one activity plus the updated session), `event: session` (a session changed without an activity: tokens, model, cost, context), `event: bank` (the bank changed) and `event: removed` (session gone). `session` and `bank` are only sent when a value really changed (percent rounded to 0.1, dollars to 0.01), so a busy status line does not flood the stream. A comment line `: ping` keeps the connection alive every 20 s.

Timing checkpoints also send `event: session` every 5 seconds for observed sessions, without adding activities or refreshing their last-hook timestamp. The live client listens to these session updates as well as activities.
The client also consumes `bank` events, so payouts and local-day rollover update without a page reload. Copilot `earned` activities occur when a saved cumulative AIC checkpoint advances, independently of Claude's delayed end-of-turn payouts.

== Server

[source,shell]
----
node packages/server/src/index.ts [--port 4747] [--host 127.0.0.1] [--approvals | --no-approvals]
                                  [--approval-timeout 60] [--open] [--quiet]
----

.Settings, from lowest to highest priority
. `~/.agent-village/config.json` (created on first run, file mode 600; holds the `token`, and `port`, `approvals`, `approvalTimeoutSec`, `wrappedStatusLine` saved by `pnpm hooks:install`, and `copilot` `{ username, githubToken, monthlyAllowance }` saved by `pnpm copilot:setup`).
. Environment variables: `AGENT_VILLAGE_PORT`, `AGENT_VILLAGE_HOST`, `AGENT_VILLAGE_APPROVALS` (`1`/`0`), `AGENT_VILLAGE_APPROVAL_TIMEOUT`, `AGENT_VILLAGE_ALLOWED_HOSTS` (comma-separated extra Host names), `AGENT_VILLAGE_HOME` (moves the config folder; used by tests).
. Command-line flags.

.HTTP endpoints
[cols="1,2,1,3"]
|===
| Method | Path | Auth | Purpose

| POST | `/hooks` | token header | Receives every Claude Code hook. Answers `200` with an empty body, or a decision for `PermissionRequest`.
| POST | `/hooks/copilot?event=<name>` | token header | Receives every GitHub Copilot hook (from `scripts/copilot-hook.ts`). Always answers `200` with an empty body at once.
| POST | `/api/statusline` | token header | The JSON Claude Code passes to its status line. Updates the session (model, cost, context) and the Claude part of the bank. Answers `200` at once.
| GET | `/events` | `?token=` | Server-Sent Events stream (snapshot, activities, removals).
| GET | `/api/state` | `?token=` | Current snapshot as JSON.
| POST | `/api/permissions/:id` | token header | Body `{"decision":"allow"\|"deny"}`. Answers a held `PermissionRequest`. `409` when it is no longer waiting.
| GET | `/api/health` | none | `{ ok, name, version, approvals, sessions }`. Used by the town to detect the server.
| GET | everything else | none | The built town from `packages/web/dist`, with the token injected into `index.html`.
|===

The token header is `X-Agent-Village-Token`. Copilot hooks go to `/hooks/copilot` with the event name in the query (see <<copilot>>). For forwarders installed before that route existed, `POST /hooks` with `X-Agent-Village-Agent: copilot` and `X-Agent-Village-Event` still works.

[[security]]
=== Security model

The server can approve commands on your computer, so it is locked down:

* It listens on `127.0.0.1` only, unless you pass `--host`.
* Every request must have a `Host` header of `localhost`, `127.0.0.1` or `[::1]` (or one listed in `AGENT_VILLAGE_ALLOWED_HOSTS`). This blocks DNS-rebinding attacks from websites.
* Hooks and the API require the random token from `~/.agent-village/config.json`. The page gets it injected by the server; other websites cannot read it because the server sends no CORS headers.
* `POST /api/permissions` also rejects foreign `Origin` headers.
* The page is served with a strict Content Security Policy (`default-src 'self'`). Fonts are bundled; the town loads nothing from the internet.
* Prompts, paths and commands stay in memory only and are never written to disk.
* *Session timing.* Only IDs, timestamps and aggregate work/wait/idle durations are stored in the private local `session-times.json` file (see <<session-time>>). Historical sessions are not restored as active robots until a new hook arrives.
* *Payout history and Copilot AIC.* `payouts.json` contains only session IDs, units, cumulative totals and daily totals. Copilot reads are limited to UUID session IDs observed through hooks and `.jsonl` real paths within `COPILOT_HOME/session-state` (default `~/.copilot/session-state`); escaping symlinks are rejected. Only AIC amounts and checkpoint timestamps are retained, never local event content. This read-only source needs no GitHub token.
* *Transcripts.* To count tokens the server reads Claude Code transcript files, read-only and only when the file ends in `.jsonl` and its real path (after resolving links) is inside the Claude config folder (`CLAUDE_CONFIG_DIR` or `~/.claude`). Any other path named in a hook is ignored. Only the four token counters and the model id are kept; nothing from a transcript is stored or sent to the browser.
* *GitHub.* With `pnpm copilot:setup` the server makes one outbound HTTPS call to `api.github.com` (at start and every 10 minutes, 10 s timeout) with your GitHub token. Nothing else leaves the computer. The token is kept in `~/.agent-village/config.json` (file mode 600), never logged, never printed and never sent to the browser. Give it only the "Plan" user permission (read).
* The status line script posts to the local server only (300 ms timeout) and never prints errors into Claude Code.

WARNING: Do not expose the port to your network or the internet. To use a tablet on your home network, see <<roadmap>>; a safe way (for example Tailscale) is planned.

[[hooks]]
== Claude Code hooks

`pnpm hooks:install` adds one entry like this for each observed event to `~/.claude/settings.json` (or `<project>/.claude/settings.local.json` with `--project`):

[source,json]
----
{
  "hooks": {
    "PreToolUse": [
      { "hooks": [ { "type": "http", "url": "http://127.0.0.1:4747/hooks", "timeout": 5,
                     "headers": { "X-Agent-Village-Token": "<token>" } } ] }
    ]
  }
}
----

* Observed events: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `Stop`, `SubagentStart`, `SubagentStop`, `SessionEnd`.
* With `--approvals` it also adds `PermissionRequest` with a timeout 15 s longer than the server's own wait, and saves `approvals: true` in the config.
* Your other hooks are left untouched. Ours are recognised by the `/hooks` URL plus the token header, so uninstall removes only them.
* A copy of the settings file is saved in `~/.agent-village/backups/` before every change.
* Open Claude Code sessions load hooks at start. Restart them (or review hooks with `/hooks`) after installing.

[[statusline]]
=== The status line

`pnpm hooks:install` also sets the status line in the same settings file (skip it with `--no-statusline`):

[source,json]
----
{ "statusLine": { "type": "command", "command": "node \"<repo>/scripts/statusline.ts\"" } }
----

* Claude Code runs it after each answer and passes JSON on stdin. The script prints the status line first (default: `Opus · ctx 23% · 5h 38% · 7d 59%`), then posts the same JSON to `POST /api/statusline` (300 ms timeout). It never fails, hangs or prints errors.
* Fields used (checked at https://code.claude.com/docs/en/statusline on 2026-10-20): `session_id`, `model.id`, `model.display_name`, `cost.total_cost_usd`, `context_window.used_percentage`, `rate_limits.five_hour` / `seven_day` / `spend_limit` with `used_percentage` (0–100) and `resets_at` (epoch seconds). `rate_limits` appear only on Pro and Max plans (or with a spend limit) and only after the first answer; every part may be missing.
* *Your own status line is kept.* If the settings file already had one, it is saved as `wrappedStatusLine` in `~/.agent-village/config.json`; the script runs it with the same input (1 s timeout) and prints its output instead of the default line. `pnpm hooks:uninstall` puts it back. Ours is recognised by the path `scripts/statusline.ts`.
* Claude Code picked up a newly installed status line in a running session in our test; if yours does not, restart the session.

.How failures behave (from the Claude Code hooks documentation)
* If the server is not running, the HTTP call fails and Claude Code continues normally (a non-blocking hook error).
* An empty `200` body means "no decision": Claude Code continues with its usual behaviour.
* For `PermissionRequest`, the server answers `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}` or the same with `"behavior":"deny"` and a `message`.

NOTE: Field names were checked against the Claude Code hooks reference (https://code.claude.com/docs/en/hooks) on 2026-10-19. The exact deny fields and some per-event input fields (`notification_type`, `last_assistant_message`, `error`) are read defensively; verify them when Claude Code changes.

[[copilot]]
== GitHub Copilot

GitHub Copilot has hooks too, in two places, and both read the same user file: `~/.copilot/hooks/*.json` (`%USERPROFILE%\.copilot\hooks\` on Windows; `COPILOT_HOME` moves it).

* *Copilot CLI* (the `copilot` command line tool).
* *VS Code agent mode* (Copilot Chat, "Local" sessions; hooks are a preview feature there, `chat.useHooks` is on by default).

=== Hooks: Copilot robots

`pnpm hooks:install` (or `pnpm hooks:install --copilot` for Copilot only) writes one file of its own there, `agent-village.json`, and `pnpm hooks:uninstall` (or `--copilot`) deletes it. Each Copilot event runs a command hook:

[source,json]
----
{ "version": 1, "hooks": { "preToolUse": [ {
  "type": "command", "timeoutSec": 5,
  "bash": "node \"<repo>/scripts/copilot-hook.ts\" preToolUse 2>/dev/null || true",
  "powershell": "& node '<repo>\\scripts\\copilot-hook.ts' preToolUse 2>$null; exit 0" } ] } }
----

* Events: `sessionStart`, `userPromptSubmitted`, `preToolUse`, `postToolUse`, `postToolUseFailure`, `notification`, `permissionRequest`, `agentStop`, `subagentStart`, `subagentStop`, `errorOccurred`, `sessionEnd`. VS Code fires only the ones it knows (no `notification`, `permissionRequest`, `errorOccurred` or `sessionEnd`).
* `scripts/copilot-hook.ts` reads the payload from stdin, reads port and token from `~/.agent-village/config.json`, posts to `POST /hooks/copilot?event=<name>` (2 s timeout) and always exits `0` with no output. This matters: Copilot CLI treats a *failing* `preToolUse` command hook as "deny", so the village must never fail. The shells add a second guard (`|| true`, `exit 0`) in case Node or the script is missing. Measured on Windows: about 0.3 s per event when the town is off.
* `packages/server/src/copilot.ts` turns both payload styles into the Claude Code shape: Copilot CLI's camelCase (`sessionId`, `toolName`, `toolArgs` as JSON text, `toolResult`, `error` as an object) and VS Code's snake_case (`session_id`, `tool_name`, `tool_input`). Event names: `userPromptSubmitted` → `UserPromptSubmit`, `agentStop` → `Stop`, `errorOccurred` → `StopFailure` (or a notification when `recoverable`), `notification_type: agent_idle` → `idle_prompt`.
* Tool names are translated to their Claude Code equivalents (`TOOL_ALIASES` in `packages/shared/src/index.ts`), so stations, labels and verbs need one list: Copilot CLI `view` → `Read`, `edit`/`str_replace_editor`/`apply_patch` → `Edit`, `create` → `Write`, `bash`/`powershell` → forge, `grep`/`rg`/`glob`, `web_fetch`/`web_search`, `ask_user` → question, `task`; VS Code `read_file`, `list_dir`, `file_search`, `grep_search`, `replace_string_in_file`, `create_file`, `run_in_terminal`, `fetch_webpage`, `manage_todo_list`, `runSubagent`… Unknown tools go to the plaza.
* Copilot robots use the same name pool, get session ids `copilot:<sessionId>`, a purple antenna bulb and a "Copilot" mark on the name tag.
* *Watch only.* Copilot's `permissionRequest` runs *before* permission rules, session approvals and `allow-all`; it is not evidence that a user prompt is displayed, so it does not change the robot's state. Only a `notification` with `notification_type: permission_prompt` makes the robot wave with "!"; `ask_user` and `elicitation_dialog` still show "?". Untyped messages mentioning permissions are informational, not a reason to wait. You answer in the terminal. The server answers every Copilot hook at once with an empty body and never holds it, even with approvals on (Copilot CLI's own answer format would be `{"behavior":"allow"|"deny"}`; VS Code has no such hook).
* Why not `type: "http"`: Copilot allows plain `http://localhost` only with the environment variable `COPILOT_HOOK_ALLOW_LOCALHOST=1`, and *never* for `preToolUse` and `permissionRequest` (they must use `https://`), and VS Code runs only command hooks. With http hooks the robots would not see tool calls, so the command hook stays and *no environment variable is needed*.

[[copilot-aic]]
=== AIC per Copilot CLI robot (no billing setup)

Copilot hooks themselves carry no model or usage counters, but current Copilot CLI writes `session.usage_checkpoint` events to `~/.copilot/session-state/<id>/events.jsonl`. The village reads `data.totalNanoAiu`, divides by `1_000_000_000` for display, and uses the event timestamp for daily attribution. A real local checkpoint of `1555360500000` matches the CLI's `1555.36 AIC` display. Generic `cost`, premium-request counts and token counts are not used as AIC; `session.usage_record` is deliberately not added on top of cumulative checkpoints.

Reads happen on hooks and every 5 seconds for tracked sessions. Saved checkpoints may lag behind the terminal's in-progress counter. This is an *internal CLI file format, not a stable public API*: versions without these fields, unreadable files and VS Code sessions without matching CLI files show an explicit unavailable/error hint. Existing known totals are retained on errors. No organisation billing access or `copilot:setup` is needed, including for company-funded CLI sessions. This is local session usage, not the company's total invoice or remaining allowance. Models and Copilot token breakdowns are not exposed by this feature.

[[copilot-vault]]
=== The Copilot vault (premium requests)

The optional right vault implements the older *premium-request* quota, not AIC or money. It is independent of local AIC earnings and requires a manually configured allowance and GitHub token:

. *Create the token.* On GitHub open *Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token*. Give it a name (for example "Agent Village"), an expiry date, and under *Account permissions* set *Plan* to *Read-only*. Nothing else. Click *Generate token* and copy it.
. *Save it in the town.* In the project folder run (your GitHub user name, and your plan's monthly premium requests: 300 for Copilot Pro, 1500 for Pro+):
+
[source,shell]
----
pnpm copilot:setup --user <your-github-name> --allowance 300
----
+
Paste the token when asked; it is not shown while you paste. (Or set `AGENT_VILLAGE_GITHUB_TOKEN` before running the command.) The script checks the token with GitHub once and prints this month's usage.
. *Restart the town* (`pnpm start`). The server asks GitHub at start and every 10 minutes. On an error it keeps the last value and the bank card shows a small warning.

To disconnect: `pnpm copilot:setup --off` (deletes the token from the config file).

* Endpoint (checked at https://docs.github.com/en/rest/billing/usage on 2026-10-20): `GET /users/{username}/settings/billing/premium_request/usage?year=YYYY&month=M`, header `X-GitHub-Api-Version: 2026-03-10`. The server adds up `grossQuantity` of the `usageItems` whose product or SKU is Copilot and whose unit is requests.
* This endpoint covers Copilot plans you pay for yourself. If an organisation pays for your Copilot, GitHub answers 404 and the vault stays grey.

NOTE: Checked against the Copilot CLI hooks reference (https://docs.github.com/en/copilot/reference/hooks-reference, again on 2026-10-20) and the VS Code hooks reference (https://code.visualstudio.com/docs/agents/reference/hooks-reference) on 2026-10-19. Real Copilot CLI hooks on macOS confirmed permission pre-checks arriving between `preToolUse` and `postToolUse`, including long-running commands; they must not be treated as human prompts. Other mappings were checked with simulated payloads through `scripts/copilot-hook.ts`. The billing API was tested with a mocked GitHub only. VS Code tool names are not listed in its documentation; the ones above are best known and should be checked in the VS Code agent debug log.

== The town (web)

* Vite + TypeScript + three.js 0.170, no UI framework. The town is drawn with toon materials and rounded shapes; robots are built from primitives in code (no model files). Fonts (Fredoka, Rubik, JetBrains Mono) come from `@fontsource` packages and are bundled, so nothing loads from the internet.
* `world/` builds the scene once and knows nothing about agents. `agents/controller.ts` keeps one `Robot` per session; `agents/robot.ts` decides what each robot shows. `ui/` renders the HUD and panel with plain DOM.
* *Pacing.* Real agents run tools in milliseconds, so each robot has a queue of *beats*. Consecutive steps at the same station merge into one visit. A beat lasts 1.7 s (1.2 s for thinking), down to 0.5 s when the queue grows; walking speeds up too. While a tool is still running (a long build, a long search), the robot keeps working at that station. After a tool, a robot that is still "thinking" walks to the fountain after a few seconds.
* *Attention first.* A permission request or a question clears the robot's queue: it walks straight to the station of the tool in question and waves (! or ?). The bubble, counters and queue chips appear at once, even while it walks.
* *Real data in the panel.* The panel's "Now" line, the request box, the *Earned* section and the log always show the real current state, not the animation.
* *Bank.* `world/town.ts` builds the bank at 10° on the outer ring (cream walls, gold-brown pediment, four columns, steps, a coin sign in front and a big coin turning on the roof) with the two glass vaults; `setVaults()` sets their fill and the coins move there smoothly. The controller batches visual rewards until the robot finishes its queued work and heads back to the charger. `world/coins.ts` flies staggered coins along an arc (~1.4 s per coin) to wherever the robot is when they land, and completes only after all coins arrive. `ui/bank.ts` owns the label above the bank, the HUD chip (hidden on phones) and the bank card. Numbers use `Intl.NumberFormat` compact notation in the UI language ("18 tys." / "18K").
* *Feed and queue chips.* Each line is short enough for its bar: shell commands show only their first command (`git add readme.adoc …`), paths only their last two folders, URLs only host and path (`shortTarget` in `ui/format.ts`). The full text is in the tooltip, and a click opens the robot's panel. Lines and chips are updated in place instead of being rebuilt, because live agents send several events per second and a rebuilt element would swallow the click.
* *Floating labels.* Robot names and the bank label use 2D positioning, with their top-left corner snapped to physical pixels after centering (including Retina displays). They do not force separate compositor layers, keeping small text sharp while the labels follow the scene.
* *Live and demo.* On start the page reads the token from `<meta name="agent-village-token">` (the server fills it in) and calls `/api/health`. If both work, it connects to `/events`; otherwise it starts the demo and says so in the feed. The *Live / Demo* switch changes source at any time; `?demo` in the URL forces the demo. Both sources speak the same `ServerMessage` format (`agents/source.ts`).
* *Demo bank.* Claude robots simulate tokens, models, costs and limits; Copilot robots simulate AIC, without a token breakdown. Both pay at the end of simulated turns, update daily totals and show lifetime earnings. The optional premium-request vault is also simulated. None of these numbers are persisted or mixed with live payouts.
* *What only the demo can do.* Answering questions, messages, *Stop* and *New robot* are simulated in the demo. Live, the panel shows the request and tells you to answer in the terminal, except permissions with approvals on (see <<hooks>>). Steering live agents is stage 3.
* *Language.* English and Polish, chosen from the browser language and remembered in `localStorage`. Demo texts are stored in both languages, so switching also changes what is already on screen.
* *Prototype.* `prototype/agent-village-prototype.html` is the original single-file version that defined the look. Keep it as a reference; do not develop it further.

[[decisions]]
== Decisions

[cols="1,3"]
|===
| Decision | Why

| Local web app (server + browser), no Next.js | No server rendering or routing needed; one long-running process must keep state in memory and hold permission requests for minutes, which Next.js dev reloads would break. A small server and a static Vite build are also easier to ship as `npx` or a desktop app later.
| Server with zero runtime dependencies | It starts instantly, needs no install, and the code that can approve commands stays small enough to read in one sitting.
| Claude Code `http` hooks instead of hook scripts | Works the same on Windows, macOS and Linux, no shell scripts to maintain, and failure is non-blocking by design.
| Server-Sent Events instead of WebSockets | Data flows one way (server → town); the few commands go over plain `POST`. SSE reconnects by itself and needs no library.
| three.js without a framework | The prototype is plain three.js; porting it 1:1 keeps the approved look. React Three Fiber would add weight without benefit here.
| Colour management off, light units scaled | Keeps the exact colours of the approved r128 prototype on current three.js: ambient, hemisphere and sun light ×π; point lights (lamps, forge) use decay 1 and ×2.8. Checked by rendering the prototype with r128 and the new town with r170 side by side, by day and by night: average colours differ by less than 3%.
| Robots, English names, bilingual UI | Requested for a more professional presentation; Polish stays available.
| Colour families per agent (warm Claude, cool Copilot) | The author wants to see at a glance which agent a robot comes from. One colour per agent would make robots of the same agent look identical, so each agent gets a family of shades.
| Copilot through a command hook and the same `/hooks` endpoint | Copilot cannot post http hooks to localhost by default, and VS Code runs only command hooks. Translating Copilot payloads on the server into the Claude Code shape keeps one state machine and one town for every agent.
| Copilot keeps the command hook, now posting to `/hooks/copilot?event=` | Copilot http hooks to localhost need `COPILOT_HOOK_ALLOW_LOCALHOST=1` and are not allowed at all for `preToolUse` and `permissionRequest`, so http hooks would hide every tool call. The forwarder needs no environment variable and also works in VS Code. A separate route with the event in the query keeps the Copilot path explicit.
| Tokens from the transcript, not from hooks | Hooks carry no token usage. The transcript has `message.usage` for every API call. Reading it later (~1.5 s after the hook, incrementally) keeps hook answers instant. Each `message.id` is counted once because Claude Code writes one line per content block with the same usage.
| Model, cost and limits from the status line | It is the only documented place where Claude Code shares `rate_limits`, the display name of the model and its own cost estimate. Wrapping an existing status line keeps the user's own line.
| Local Copilot AIC, separate from the optional premium-request vault | Local cumulative checkpoints match the CLI's AIC counter without billing access; native nano-AIC integers avoid rounding drift. The existing optional billing API integration remains a separate premium-request quota, not an AIC allowance.
| Persistent cumulative payouts | Saving daily totals and session high-water marks together avoids duplicate payouts after restart. Claude tokens and Copilot AIC remain separate units.
| Cache reads count as earned tokens | The robot "earns" every token its session used. Cache reads are usually the largest part; leaving them out would hide most of the work.
|===

== Troubleshooting

No robots appear::
. Is the town running (`pnpm start`) and does `http://localhost:4747/api/health` answer?
. Are the hooks installed? Run `pnpm hooks:status`.
. Restart the Claude Code session; it loads hooks only at start.
. Port changed? Run `pnpm hooks:install --port <port>` again.

"Port 4747 is already in use":: The town is probably already running in another terminal. Open `http://localhost:4747`, or start on another port with `node packages/server/src/index.ts --port 4848` and reinstall the hooks with `--port 4848`.

Claude Code shows hook errors when the town is off:: Expected: each hook call fails fast and Claude Code continues. Start the town, or run `pnpm hooks:uninstall` while you do not use it.

The page says the town is not built:: Run `pnpm install` and `pnpm build`, then refresh.

The town is black or empty:: Your browser needs WebGL. Try Chrome, Edge, Firefox or Safari with hardware acceleration on.

The town shows the demo although the server is running:: Open the town from the server itself (`http://localhost:4747`), not from a saved file or another port: only the server puts the token into the page. During development use `http://localhost:5173` after the server has run once (it creates `~/.agent-village/config.json`, which Vite reads). Then click *Live*.

The bank is empty (grey Claude vault)::
. Limits appear only on Claude *Pro* and *Max* plans, and only after the first answer of a session.
. Is the status line installed? Run `pnpm hooks:status`. If it says "another one", run `pnpm hooks:install` again (your line keeps showing).
. Restart Claude Code sessions after installing the status line if the numbers do not come.

The Copilot vault is grey or shows a warning::
. Not connected: run `pnpm copilot:setup --user <name>` and restart the town.
. 401: the token expired or was revoked; make a new one. 403: the token needs the "Plan" permission (read). 404: wrong user name, or your Copilot is paid by an organisation (not supported yet).

A Copilot robot shows "—" under Earned:: No supported local CLI AIC checkpoint is available yet. Let the CLI finish a turn; inspect the error in the robot panel and server terminal. The server must run as the same user and with the same `COPILOT_HOME` as the CLI. VS Code sessions without a CLI event file are not supported for AIC. Do not configure the premium-request vault to fix local AIC.

`pnpm setup` did something strange:: That is pnpm's own command for installing pnpm. The project's command is `pnpm first-run`.

== Glossary

Session:: One running Claude Code or GitHub Copilot conversation. One session = one robot.
Hook:: A Claude Code setting that calls a command or URL when something happens (a tool runs, a prompt is sent…).
Activity:: One event in the town's own format, made by the server from a hook.
Station:: A place in the town where robots do one kind of work.
Beat:: One step a robot shows on screen; several quick tool calls can merge into one beat.
Approvals:: The optional mode in which the town answers Claude Code's permission questions.
Bank:: Daily robot payouts, separately in Claude tokens and Copilot AIC, plus two optional provider-limit vaults.
Earned:: Cumulative session payouts: transcript tokens for Claude or locally checkpointed AIC for Copilot CLI. Animated coins are not currency or a conversion rate.
Status line:: The line under the Claude Code prompt. Its command gets JSON with the model, cost and plan limits; Agent Village's script shows the line and forwards the JSON to the town.
Premium request:: The older quota unit used by the optional Copilot vault. Not AIC, tokens or money.
AIC:: AI credits reported locally by Copilot CLI. Native `totalNanoAiu` values represent billionths of one AIC; the UI displays two decimal places.
